# Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Optional accounts that only appear when they're needed: email magic link and Google, with no passwords. Hearts and collections sync across devices, and nothing personal is ever readable without a verified session.

**Architecture:**
- **Sign-in:** Arctic (a small OAuth library) handles Google. Email links are single-use with hashed tokens.
- **Sessions:** stored in Neon, following the Lucia session guide: a random token in the cookie and its SHA-256 as the row id.
- **Pages:** they never read cookies, so they stay edge-cacheable. The browser asks `/api/me` (never cached) who is signed in.

**Tech Stack:** Next 16 on Workers, Neon, Resend, Arctic, WebCrypto, bun test.

**Spec:** `docs/superpowers/specs/2026-11-12-pro-program-design.md` (§5.2, §6.1, §9 items 1, 5, 9)

## Global Constraints

- $0. The Worker bundle stays ≤ 2000 KiB gzip (1888 today), so no auth framework.
- Owner's choices:
  - Sign-in is a small sheet over the library.
  - Signed out, the header shows a quiet "Sign in" link; signed in, the person's initial in a circle.
  - The sign-in email is plain: lens mark, one line, one button.
  - Google and email are both offered.
- Pages and public APIs must not read cookies or vary per person. Personal data comes only from `/api/me*` and `/api/auth/*`, which are never edge-cached.
- Nothing is returned by email alone. Every personal read needs a valid session.
- Tokens: 20 random bytes in base32. The database stores only the SHA-256. Email links expire after 15 minutes and work once. Sessions last 30 days and renew when fewer than 15 days remain.
- Cookies: `hl_session`, httpOnly, Secure, SameSite=Lax, path `/`. The OAuth state and PKCE verifier live in cookies for 10 minutes.
- Every write route is guarded: rate limited, or `// guard: none — reason`. `bun run check` enforces it.
- Changelog lines of 8–16 words. A README section. Phosphor bold icons. BDO Grotesk. The Pro card's visual language: one surface, hairlines, ticket-stub actions, no pill buttons.

## Review Focus

1. **A link opened in a different browser:** it still signs the person in, in that browser, and the token is consumed.
2. **Two devices with conflicting local collections:** the merge is a union per set, and nothing is lost.
3. **A forged or replayed OAuth state, or a used or expired link:** clear error copy, no session.
4. **An edge-cache leak:** `/api/me` or an auth redirect gets cached and served to someone else. Every auth and me route must stay out of `cacheKind`.
5. **Delete account:** the user row, sessions, data and the subscriber link are all removed, and the cookie is cleared.

### Task 1: Schema
- Create `scripts/025-accounts.sql`, adding:
  - `users` (`id uuid pk default gen_random_uuid()`, `email text unique not null` stored lowercase, `name text`, `avatar_url text`, `google_sub text unique`, `member_no serial unique`, `created_at timestamptz default now()`)
  - `sessions` (`id text pk`, `user_id uuid references users on delete cascade`, `expires_at timestamptz not null`, `created_at`)
  - `login_tokens` (`id text pk`, `email text not null`, `expires_at timestamptz not null`, `used_at timestamptz`, `next text`)
  - `user_data` (`user_id uuid pk references users on delete cascade`, `favorite_ids int[] not null default '{}'`, `collections jsonb not null default '{}'`, `updated_at`)
  - Indexes on `sessions(user_id)` and `login_tokens(expires_at)`.
- Apply it to Neon, and record the result in the ledger.

### Task 2: Session core (`lib/auth/session.ts`), test first
- `generateToken(): string`, `hashToken(t: string): Promise<string>`
- `createSession(userId, deps?) → { token, expiresAt }`
- `validateSession(token, deps?) → { user, session } | null`: renews when less than 15 days remain, and deletes expired sessions.
- `invalidateSession(id)`, `sessionCookie(token, expires)`, `blankSessionCookie()`
- Tests use a fake `sql`:
  - an expired session returns null and is deleted
  - a session near expiry is renewed
  - the token itself is never stored, only its hash

### Task 3: Email magic link (`lib/auth/magic-link.ts`), test first
- `requestLink(email, next, deps) → void`: rate limited to 5 per hour per email and 20 per hour per IP; stores the hash; sends the plain email.
- `consumeLink(token, deps) → { userId, next } | { error: 'expired' | 'used' | 'invalid' }`: creates the user if this email is new, then marks the token used in the same statement.
- `next` must be a same-origin path, otherwise `/`.
- Tests:
  - expired, used and unknown tokens are rejected
  - an unsafe `next` such as `//evil.com` or `https://x` becomes `/`
  - an email that isn't a valid address is rejected without a send

### Task 4: Google (`lib/auth/google.ts`)
- Arctic `Google(clientId, secret, redirectUri)` with PKCE and state cookies.
- On the callback, check state, exchange the code, read the id_token claims, and require `email_verified`.
- Find the user by `google_sub`, then by email (links an existing email user), or create one.
- Tests cover the claims mapping and the account-linking rule with fakes.
